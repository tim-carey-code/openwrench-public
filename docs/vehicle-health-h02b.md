# H02B structured diagnostic context acquisition

H02B permits one live structured health input: standard Mode 01 PID `0103` fuel-system status. It adds no rule, threshold, finding, UI control, or automatic health requirement. A future health owner must explicitly call `NativeController.setHealthRequirements` while acquisition is stopped, then explicitly start live acquisition. No physical adapter or vehicle was used in development or tests.

## Boundaries and provenance

- `NativeSession.readStructured(pid)` accepts only `0x03`, checks current-session advertised support before an exchange, and uses the existing 3-second standard read timeout, 4096-byte response ceiling, ASCII/framing checks, single unaddressed response rule, and fault cleanup. `NO DATA` returns a null value. All other structured PIDs and the scalar `read` path remain disallowed for this call.
- `ObdDecoder.decode` supplies the existing structured `system_1` and `system_2` values. The health bridge preserves `SignalValue.Structured` and PID `0103`; it never substitutes a scalar. Live unaddressed ELM responses provide no verified module identity or ECU timestamp, so both fields remain null. The app records its monotonic completed-read receipt, hardware source, and session generation.
- `HealthInputPlanner.plan` gives each requirement a scalar, structured, or unknown kind. Scalar `acquisition` and health-only `structured` maps are separate. A structured requirement is admitted only for `fuel-system-status`, only when PID `03` is advertised by the current session, and only when the dashboard selection is empty. If health-only scalar and structured inputs are both requested, the first eligible type is admitted and the later type is deferred as `CADENCE_CONFLICT`; duplicate requirements share the admitted request. `NOT_ADVERTISED`, `NOT_ALLOWLISTED`, and `CADENCE_CONFLICT` explicitly describe deferral. Disconnected plans are rechecked after a new connection discovers capabilities.
- `NativeController` merges due scalar and structured work in its existing serialized I/O worker. It does not create another session or scheduler. Structured results enter only the bounded health observation window; dashboard readings and scalar watch settings stay unchanged. Unavailable, stale, disconnected, and error receipts supersede earlier available evidence. Stop, cancellation, reconnect, and generation checks prevent late reads from republishing previous evidence.

## Timing and future rule limits

H02A's conservative five-second gauge freshness policy also applies to `0103`. With any dashboard PID selected, an additional health request is deferred: two 3-second bounded reads plus the 200 ms inter-read spacing can exceed that freshness limit. The same worst-case spacing prevents admitting `0103` alongside a health-only scalar even when the dashboard selection is empty. A fast prior response cannot guarantee a fast next response. Alone, structured health acquisition can proceed at the planner's Normal 2-second target, subject to actual serialized adapter latency. Measured receipt spacing and receipt age remain the authority for evidence freshness; admission is not an ECU sample cadence or delivery guarantee.

H03 rules must independently review applicability, source, freshness, sample windows, unknown module identity, and `NO DATA` or malformed responses. A fuel-system status code alone does not diagnose a fault or establish a vehicle-specific reference range. Scripted transport tests check the code paths and worst-case admission policy; they do not qualify Bluetooth, USB, ELM327 variants, vehicles, or real gauge timing.
